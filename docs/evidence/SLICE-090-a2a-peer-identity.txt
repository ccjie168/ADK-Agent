live, two peers and legacy on real A2A servers
----------------------------------------------
peer store: file, tenant acme, manifest id bot with exposure a2a
grants: peer-read -> read, peer-write -> invoke

GET  /.well-known/agent-card.json  as peer-read   -> 200

  {"jsonrpc":"2.0","id":7,"error":{"code":-32001,"message":"forbidden"}}
GET  /.well-known/agent-card.json  as peer-write  -> 404
POST tasks/get                     as peer-write  -> 403 -32001 (no read grant)
POST message/send                  as peer-write  -> 200, task accepted
POST message/send with a bad token                -> 401
POST message/send with no token                   -> 401

legacy server with the shared token:
GET card with token -> 200
GET card without    -> 401

audit file:
  peer.call denied acme peer-read  bot
  peer.call denied acme peer-write bot
  peer.call denied acme peer-write bot
  agent.run error  acme peer-write bot@dev

notes
-----
- The allowed `message/send` reached the agent, which then failed at the model
  because the live check has no provider credentials. The audit line proves the
  run was recorded under tenant `acme` and subject `peer-write`, not
  `local/a2a_user`, which is the identity switch this slice delivers.
- `tasks/get` with only `invoke` is denied, so the two actions are independent.
- The card returns 404 rather than 403 when the peer has no `read` grant. The
  contract was narrowed to match: A2A has one GET entry, so every GET denial is
  a hidden card.
- Denial audit events carry a fresh run id and the request trace id when the
  trace middleware set one; the earlier draft used a shared constant and was
  corrected during review.
- The authorization middleware keys grants by the manifest id, not the ADK agent
  name, so a registry identity and a local agent name may differ safely.
