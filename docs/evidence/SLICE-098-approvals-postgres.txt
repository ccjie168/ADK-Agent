notes
-----
- Two concurrent decisions ran on two pooled connections (pool max_size=5). One
  recorded a decision, the other got ApprovalConflict.
- The expired undecided row was archived with status 'expired' by prune.
- Review fix 1: the first prune SQL only matched terminal statuses, so a request
  that expired without anyone deciding stayed 'pending' forever and was hidden
  from pending(). It now counts rows with status 'pending' and a past expires_at
  as terminated, and archives them as 'expired'.
- Review fix 2: pruning a reused request id raised UniqueViolation on the archive
  insert. The insert is now ON CONFLICT (request_id) DO NOTHING, and the live
  row is left in place, matching FileApprovalInbox's `kept` behavior.
- Review fix 3: for expired rows the prune cutoff now uses expires_at, not
  requested_at, matching the file implementation's deadline.
- PruneResult.kept stays 0 for the Postgres inbox. The CLI only prints archived
  or deleted counts, so the field is not observable.
- Observed clock skew: the host clock was about 4 s ahead of the Postgres
  container. An expires_at of "now minus 1 second" on the host was still in the
  future by server time, so the decision was accepted. Expiry is judged by the
  database's now(). Keep app and database clocks NTP-synced, and size approval
  deadlines well above the skew. The live driver uses a one hour margin.
- Idempotent submit compares the effective expiry, so a ttl-derived deadline is
  stored and returned by get(). FileApprovalInbox returns the raw request with
  expires_at=None. Stored deadlines are the deliberate difference.
- No RLS in v1. Tenant filtering, console and executor wiring are SLICE-099.
