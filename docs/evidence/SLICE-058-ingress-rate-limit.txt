$ ADK_TOOL_TOKEN=live-token adk-agent serve-tool-gateway --tools tools.py \
    --host 127.0.0.1 --port 18099 --auth-token-env ADK_TOOL_TOKEN \
    --rate-limit 3 --rate-limit-window 10
$ python probe.py   # five valid POST /v1/invoke, then GET /metrics
statuses: 200, 200, 200, 429, 429
fourth and fifth: Retry-After: 10, body {"error":"rate_limited"}
$ GET /metrics (with token)
adk_http_rate_limited_total{surface="tool_gateway"} 2
exit=0

The first live run exposed a problem: GET /metrics was itself rate limited because the scraper shares
the caller key. The three services that expose /metrics now exempt it. Re-run above shows the scrape
returning 200 while the counter reads 2.

== reading ==
- Auth runs first; requests without a token get 401 before the limiter sees them
  (tests/test_ratelimit.py::test_auth_runs_before_limit).
- The window is fixed, so Retry-After is the time until the oldest hit leaves, not a rolling estimate.
- Counts are per process and per caller key. Multi-replica deployments get one budget per replica;
  shared counting needs Redis or the ingress, which is out of scope.
- The key dict only reclaims expired keys when it reaches 4096 entries. A large wave of distinct live
  callers within one window can exceed that until their windows expire.
