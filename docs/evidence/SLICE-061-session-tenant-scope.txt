SLICE-061 session tenant scope evidence
date: 2026-11-13

== investigation ==
ADK keys sessions by (app_name, user_id, session_id). It exposes no tenant column and
generates its own SQL, so app.tenant_id cannot be injected. Both of our entry points own
the user_id they pass: the console calls the session service directly, and the MCP path
rewrites user_id in _PrincipalSessionService / _PrincipalRunner. The seam is our key,
not the ADK schema.

== live: SQLite session store, default vs scoped ==
A real console on 127.0.0.1, SQLite session DB, one chat each (the model call fails without
credentials, but the session is created before the run).

Default run:
$ adk-agent console --agents agent.py --session-db sessions.db --port 18095 ...
$ sqlite> select app_name, user_id, id from sessions;
('probe', 'console_user', 'ab90097c-...')

Scoped run, same DB:
$ adk-agent console --agents agent.py --session-db sessions.db --port 18094 --session-tenant-scope ...
$ GET /api/sessions?agent=probe
[{"session_id": "44bdcfd9-...", ...}]
$ sqlite> select app_name, user_id, id from sessions;
('probe', 'console_user', 'ab90097c-...')
('probe', 'local:console_user', '44bdcfd9-...')

The scoped console lists only the scoped session; the pre-flag row is invisible, which is the
documented migration cost of turning the flag on.

== reading ==
- The seam is our own user_id, not an ADK table change. No SQL was touched.
- Default stays `<subject>`, so existing deployments and tests are unaffected.
- Turning the flag on changes the key, so old sessions do not appear. There is no automatic
  migration; sessions are ephemeral by design.
- Transports without a principal (static token, stdio) keep `mcp_user` / `console_user` semantics.
