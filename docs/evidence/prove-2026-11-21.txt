一、方法

- 每个检查启动真实进程或真实容器，走 HTTP/SDK 调用，直接查询 Postgres 里落下的审计行；不 mock 服务边界。
- Postgres 使用 `pgvector/pgvector:pg15` 容器（临时启动、随机端口、随机口令、结束即删除），向量扩展由 `PgVectorRagStore` 自己创建。
- 模型与嵌入走本地 OpenAI 兼容桩（`/v1/chat/completions`、`/v1/embeddings`），经真实 `litellm` 通道调用；不访问外部 API，不使用任何真实密钥。
- 完整一轮耗时约 166 秒；日志与 `report.json` 写入临时工作目录，默认跑完删除，加 `--keep` 才保留。
- 运行前需在虚拟环境安装声明过的 `[litellm]` extra；按未锁定版本直接解析会引入带已知漏洞的
  `wcmatch`，开发环境应在跑完验收后恢复依赖，生产与 CI 仍按 `requirements/runtime.lock` 安装。
- 容器镜像取自本机可达的镜像源；默认跑完删除临时工作目录（含生成的签名私钥），需要保留时加 `--keep`。

四、已知限制（本次没有覆盖）

- 沙箱执行（POSIX-only）在 Windows 上不可用，`sandboxed` 路由未在本机跑通。
- 多副本 Kubernetes 清单没有集群可部署，只有文本级守卫测试。
- 真实外部模型与嵌入通道（Gemini/Claude/DeepSeek）未调用；RAG 排序质量与真实 LiteLLM embedding 仍未验收。
- OIDC 登录链路没有真实 IdP；浏览器 UI 未做自动化点击。
- Redis 跨副本限流未在本轮复跑（既有证据见 SLICE-084）。

五、本轮发现

1. console 启动时用 `--agent-ref` 加载的 agent 没有检索上下文：`_register` 的启动循环不传 manifest，而 `rag.context` 只在按需加载路径构造。按需加载路径已验证可用。属真实缺口，建议单开切片。
2. `triggers register --digest` 要求 `sha256:` 前缀，而注册表记录里是裸 hex；触发服务会归一化，所以能用，但命令行容易踩。
3. 无 OIDC 的 console 主体租户固定为 `local`，RAG 只能看到该租户的文档；正式部署需由 OIDC claim 提供租户，手册应写明。
