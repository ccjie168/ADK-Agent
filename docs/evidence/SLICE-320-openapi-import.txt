一、红绿说明

本轮先写 spec 与契约，然后写实现，最后补用例：**没有单独抓红屏**。实现前
`tools/openapi_import.py`、`ConnectorSpec.operations`、逐操作工具与 CLI 子命令都不存在，
用例必然 ImportError 或断言失败；如实记录这次顺序偏差（与 SLICE-314 同）。

首轮跑用例时抓到 6 处问题并修正：`methods` 只统计被采用的操作用户预期多了 PUT、
参数化用例的 `missing_server`/`spec_invalid` 先后、假响应缺 `content_type`、
`ConnectorDenied` 的属性名是 `error_code`、CLI 对 dict 结果仍调 `model_dump`、
无参数的路径前缀被算成 `/` 导致调用被拒。

三、实现要点

- `ConnectorSpec.operations`（additive，缺省空）：`{tool_id, path, method}`；
  模型校验 `tool_id` 以 `<connector_id>.` 开头、路径以 `/` 开头且无 `..`。
- `tools/openapi_import.py` 纯函数：`servers[0].url`（或 `--base-url`）→ `base_url`；
  每个 `operationId` 一个工具；`x-data-classes`/`x-risk-level` 扩展；上限 200；
  `skipped` 列出无 id 的接口。错误码见契约。
- 网关：有 `operations` 的连接器为每个操作生成一个 `ToolSpec`（工具名即 `tool_id`），
  参数是 `query`/`path_params`/`json_body`；路径参数拒绝 `/`、`\`、`..` 后再 URL 编码，
  仍过 `_path_allowed` 与出站 host 校验。没有 `operations` 的连接器行为不变。
- 工具目录：`merge_tool_entries`（幂等或冲突）、`write_tool_catalog`（临时文件 +
  原子替换）。
- CLI：`connectors import-openapi --spec --connector-id [--tenant] [--base-url]
  [--connectors-dir|--registry-url] [--tool-catalog] [--dry-run]`。

六、首轮验证修正（REJECT 后）

首轮验证 REJECT，两个阻断项与若干 N，均已修：

- **S1（安全）**：逐操作的 `risk_level`/`data_classes`/`write` 原先没传到网关
  `ToolSpec`，连接器级固定 L2/internal，导致 `x-risk-level: L3` 的写操作在网关上
  不需要审批也不要求幂等。`ConnectorOperation` 现在自带这三项，网关与工具目录都按
  操作取值；新增 `test_gateway_tool_carries_operation_governance` 与实机核对
  （`pay.refund` → risk=L3, approval=True, idem=True, classes=('confidential',)）。
- **B1**：重复 `operationId` 会产出重复 `tool_id`，工具网关启动时直接拒绝。导入期
  现在报 `duplicate_operation_id`，写入前就失败；用例
  `test_import_rejects_duplicate_operation_ids`。
- **B2（回滚）**：`ConnectorSpec` 是 `extra="forbid"`，旧版本读到带 `operations` 的记录
  会让 `FileConnectorStore.list()` 整体失败。本次不改存储行为，契约新增「回滚注意」
  一节写明回退前要删除或用旧版重新登记，并把“文件存储逐条容错”记为后续项。
- N1 路径前缀截取改为 `{` 之前（`/tickets{id}` → `/tickets`），用例
  `test_prefix_stops_before_the_first_placeholder`。
- N2 非法 `x-risk-level` 给 `invalid_risk_level`；`base_url` 不合规由
  `ConnectorSpec` 抛出的校验错误收敛成 `spec_invalid`；目录不可读给
  `catalog_unreadable`。用例 `test_import_rejects_bad_risk_level_and_host`。
- N3 `connector_tool_entries()` 对含 operations 的连接器按操作展开，不再出现
  网关没有的连接器级“幽灵工具”；用例 `test_connector_tool_entries_mirror_operations`。
- N4 补了编码正例（`T 1` → `T%201`）：`test_operation_tool_encodes_path_params`。
- N7 契约对 `..` 的措辞改为“路径段不得为 `..`”，与代码一致。

第二轮验证又 REJECT 两处，继续修：

- **B1 残留**：上一轮只拦导入入口，`ConnectorSpec` 模型本身仍接受重复
  `operation.tool_id`，控制面 POST 可写入并让工具网关启动失败。模型校验现在拒绝
  重复；用例 `test_model_rejects_duplicate_operation_tool_ids`。
- **S1 残留**：`x-risk-level` 只读操作对象，写在 path item 或文档顶层会被静默降级成
  L2；连接器级 `risk_level`/`data_classes` 不兜底。现在三个层级都会回退读取（与
  `x-data-classes` 对称），且 `ConnectorSpec.operation_governance` 把连接器级风险与
  分级当作下限（取较高风险、分级并集），网关与工具目录都用它；用例
  `test_path_item_risk_level_is_honoured`、`test_connector_risk_floor_raises_operation_tools`。
- N1 目录冲突现在有稳定码 `catalog_conflict`；N2 补 `catalog_unreadable` 与
  `catalog_conflict` 的 CLI 用例（同时断言不写入连接器）。

七、限制

- `x-data-classes`/`x-risk-level` 是平台扩展，标准 OpenAPI 文档没有这两项时统一按
  `internal`/L2 处理；连接器级 `data_classes` 固定 `internal`，逐工具的取值在目录里。
- 路径前缀取自文档的静态部分；由于逐操作工具的方法与路径是固定的、路径参数又被限制，
  前缀略宽不会带来调用方可选的路径。
- `--registry-url` 路径把带 `operations` 的连接器发给控制面，要求服务端同版本；
  未做版本协商。
- 文档里 `$ref` 参数/安全方案不解析；导入只依赖 `paths`、`servers` 与两个扩展字段。

八、范围外

- MCP 连接器（0047-2）、插件入口（0047-3）。
