notes
-----
- The first CI run after the push failed before any step: the v0.28.0
  trivy-action's composite ref to setup-trivy@v0.2.1 no longer resolves. The
  workflow now installs Trivy with the SHA-pinned setup-trivy v0.3.1 and runs
  the CLI directly, which also makes the ignore-file flag explicit.
- The second CI run failed installing the dev lock: pip-tools 7.6.2 pulls
  unpinned setuptools, which --require-hashes rejects. The dev lock is now
  compiled with --allow-unsafe, so pip 26.3 and setuptools 84.2.1 are pinned.
  A `pip download --require-hashes -r requirements/dev.lock` check exits 0.
- The third CI run passed both lock installs and failed on two gate steps.
  pip-audit found 13 filelock CVEs because the lock pins filelock 3.32.7 while
  the local venv has 4.2.10; the gate now passes the accepted IDs from
  .trivyignore.yaml to pip-audit. detect-secrets flagged a dev DSN password in
  docs/PROGRESS.md; the examples no longer embed it.
- The project install runs with --no-build-isolation in both Dockerfile and CI,
  so hatchling comes from the hash-checked lock instead of being fetched at
  build time.
- hatchling and its build-only dependencies now ship in the runtime image.
  A builder stage that keeps them out of the final image is possible follow-up
  work and is not claimed here.
- Registry push and digest write-back remain out of scope for this slice.
