# ADR-0012 跨副本限流

状态: Accepted   日期: 2026-11-14   签字: Jie CAO（会话确认）

## 背景

入口限流（SLICE-058/059）的计数在进程内。多副本时每个副本各算一份，实际允许流量是配置值的 N 倍。`docs/contracts/cli.md` 已经写明“跨副本限流交给入口网关或反向代理”，但试点部署没有统一入口，控制台和三个服务各自暴露端口。

ADR-0002 第 8 条要求状态外部化。限流计数是短命状态，不必进 Postgres，但需要一个所有副本都看得见的共享计数。

不决定的后果：副本数一加，限流形同虚设；靠入口网关又要求部署形态先统一。

## 决定

1. **共享计数用 Redis。** 新增可选后端 `redis://`，通过 `RATE_LIMIT_URL` 选择；不设置时保持进程内计数，行为不变。只新增一个可选依赖 `redis`（`redis[hiredis]` 不强制），不引入消息队列。

2. **固定窗口语义不变。** 每个服务的窗口与上限仍由 `--rate-limit`/`--rate-limit-window` 决定。键是 `adk:rl:<surface>:<key>:<window_start>`，其中窗口起点按 epoch 取整。计数用一次 Lua 脚本完成 `INCR` + 首次设置 `PEXPIRE`，避免读改写竞态。

3. **故障时放行（fail-open），但可见。** Redis 不可达时退回进程内限流（不是完全不限流），并记录 `adk_rate_limit_backend_errors_total{surface}` 指标与一次 WARNING 日志。理由：限流是保护措施，不应在缓存故障时把整个服务变成拒绝服务。需要严格拒绝的入口（对外网关）由部署方保证 Redis 可用或改用入口层限流。

4. **配置与范围。** `console`、`serve-model-gateway`、`serve-tool-gateway`、`serve-audit`、MCP 与 A2A 的 `--rate-limit` 逻辑共用同一个限流器接口；`RATE_LIMIT_URL` 是全局的。Redis 键带 surface 前缀，避免不同服务互相计数。`/healthz` 与 `/metrics` 的豁免规则不变。

5. **不做分布式令牌桶、滑动窗口、按租户的动态配额**。这些都是后续演进；固定窗口足以满足试点。

## 备选与否决

- **只依赖入口网关**：需要先统一部署形态，试点没有；保留为生产建议。
- **计数放 Postgres**：每次请求写库，延迟与写放大都不可接受；否决。
- **Redis 故障时 fail-closed**：会放大故障，缓存不可用时全站 503；否决，改为退进程内并计数错误。
- **滑动窗口/令牌桶**：需要更多状态与 Lua，收益在试点阶段不明显；后续可换实现而不改接口。

## 后果

- 副本间共享上限；Redis 成为可选的基础设施依赖，未配置时行为与今天一致。
- fail-open 留下了故障窗口内的超额流量，但有限流回退，不会完全裸奔。
- 新增一个 Redis 容器或托管实例；部署文档需要写清。
- 后续切片：Redis 实现与 Lua、六个服务的接线、指标与错误日志、跨副本压测。

## 确认记录

2026-11-14 会话确认，三点均按本 ADR 采纳：

1. 共享计数用 Redis，`RATE_LIMIT_URL` 选择，未配置时保持进程内计数；只新增可选 `redis` 依赖。
2. 固定窗口语义与键格式不变，Lua 原子 `INCR` + `PEXPIRE`，键带 surface 前缀。
3. Redis 不可达时退进程内限流（fail-open），记指标与 WARNING，不把服务变成全量拒绝。
