# ADR-0039 控制台全平台能力总览与 Ask AI 入口

状态: Accepted   日期: 2026-11-22   签字: Jie CAO（会话确认）

## 背景

平台后端能力已经成体系：审计链（ADR-0037）、共享配额、RAG 检索（ADR-0035/0036）、模型网关的别名路由与
熔断与预算（ADR-0033）、工具授权与风险分级（ADR-0028/0029/0034）、语义层（ADR-0038）。但这些能力大多
只存在于 API、CLI 与门禁测试里，控制台看不到。

控制台现状是 `src/adk_agent/console.py` 单文件内联 HTML/CSS/JS，无前端框架、无构建步骤。已有 12 个面板
（chat / runs / sessions / plans / registry / tools / connectors / credentials / peers / approvals /
grants / policy），分「运营 / 构建 / 治理」三组导航，有浅色与深色两套 CSS 变量。以下后端能力在控制台
完全不可见：

- **审计**：`audit` 模块有 `query_events` 只读查询与整链验签，控制台没有审计面板。
- **配额**：`runtime/quota_postgres` 有共享计数与并发租约，控制台没有用量视图。
- **RAG**：`rag` 模块有摄取与检索，控制台看不到语料、分块、预算与检索效果。
- **模型网关**：别名路由、降级、熔断、预算都在 `models/gateway_llm` 里，控制台没有状态面板。
- **语义层**：ADR-0038 的术语表、概念、能力绑定、确定性路由刚落地，控制台完全没暴露。

另一个短板是没有**全局 Ask AI 入口**：用户自然语言需求到 agent 能力的映射（ADR-0038 的语义路由），
在控制台里没有表达位置。也没有**通用导入**：术语表、agent 定义、RAG 语料都得靠 CLI 或手工装库。

## 决定

控制台升级为**全平台能力总览**，把后端能力可视化，并补上全局 Ask AI 入口与通用导入。视觉风格参照
Cloudflare Dashboard：侧边栏导航、卡片网格、高信息密度、克制的浅色优先配色。这里「风格」是视觉语言，
不是「必须用 React 复刻」。分五个决策。

### 1. 信息架构：总览首页 + 补全能力面板

新增一个**总览首页**，卡片网格聚合各能力的关键指标：待审批数、配额用量、RAG 分块数、模型网关熔断状态、
工具授权即将到期、语义层术语/概念/绑定数。每个卡片深链到对应面板。

在现有 12 个面板之外补 5 个只读能力面板（数据都来自已有后端查询）：

- **审计**（audit）：事件查询、整链验签状态、按租户/时间过滤。
- **配额**（quota）：运行计数、并发租约、按租户用量。
- **RAG**：语料来源、分块数、检索配置（top_k / min_confidence / data_classes）、最近检索审计计数。
- **模型网关**：别名候选、降级与熔断状态、预算余额、模型审计计数。
- **语义层**：术语表、概念层级、能力绑定、确定性路由的「命中结果」可回放。

导航从「运营 / 构建 / 治理」三组扩展为「总览 / 运营 / 构建 / 治理 / 数据」五组，语义层与 RAG 归「数据」。

### 2. 技术栈：不引入前端框架，保持无构建的服务端渲染

沿用单文件内联 HTML/CSS/JS 与 CSS 变量，用卡片系统、侧边栏与浅色优先主题达成 Cloudflare 风格。**不引入
React / Vue / Vite / Tailwind 等前端框架或构建链**。理由：

- 零新依赖，不触发「新增依赖需 ADR」的门槛，门禁仍是纯 Python 单一入口（ruff / mypy / pytest / bandit /
  pip-audit / detect-secrets），不被前端构建链破坏。
- 部署仍是单 FastAPI 服务，不起 npm 工具链、不加静态构建产物。
- Cloudflare Dashboard 的风格是可迁移的视觉语言（侧边栏、卡片、信息密度、克制配色），纯 CSS 可达。
- 控制台的交互本质是「只读查询 + 少量提交」，不依赖前端框架的响应式状态管理。

若未来需要重度交互（拖拽编排画布、实时拓扑、多人协作），另起 ADR 评估引入前端框架，不在本 ADR 范围。

### 3. Ask AI：全局入口，走语义层确定性路由

新增全局 Ask AI 入口（顶栏常驻输入框 + 独立面板）。用户输入自然语言，经 ADR-0038 的 `route_request`
做**确定性**语义路由，展示命中的概念、能力与工具，并深链到对应面板或触发。

MVP 阶段 Ask AI 只做「确定性映射展示 + 深链」，**不做**完整的多 agent 编排（计划结构选择的模型填空属
ADR-0038 第二阶段）。命中结果可审计：需求 → 概念 → 能力 → 工具，每一步可回放。

### 4. 通用导入：一个入口，三类格式

新增统一导入入口，三类格式共用同一上传、校验、落库、审计管线：

- **术语表**：CSV / JSON，落 `FileConceptSchemeStore`（ADR-0038）。
- **agent / tool 定义**：manifest，落 registry（复用现有按需加载与验签路径）。
- **RAG 语料**：文档，走 `IngestionPipeline`（ADR-0035 摄取管线）。

导入是「上传 → 校验 → 落库 → 审计」，失败给出结构化错误，不部分写入。

### 5. 验收：prove_it_works.py 里的可验证断言

每个能力面板、Ask AI、导入都在 `scripts/prove_it_works.py` 有 HTTP 级验收：起真实 console 服务，用 httpx
断言首页含各能力面板的 marker（`data-capability` 等）、调用 Ask AI 端点返回命中、调用导入端点后落库可读。
验证「能力可被前台看到、导入后数据可读、Ask AI 能确定性映射」，不验证视觉像素。

## 备选与否决

- **引入 React + Vite + Tailwind 前端框架。** 体验上限高，但引入大量新依赖与构建链，门禁、CI、部署全部
  复杂化，与平台「单 FastAPI 服务、纯 Python 门禁」的现状冲突。MVP 用不上。否决（留作远期演进）。
- **只做数据表格、不做总览首页。** 能力可见了，但没有「一眼看到全局」的总览，短板仍在。否决。
- **Ask AI 直接做模型驱动的端到端编排。** 越过了 ADR-0038 的第二阶段触发条件（确定性映射稳定后再说），
  不可审计不可复现。否决，MVP 只做确定性路由展示。
- **保持现状，只把缺失面板平铺加进去。** 不加总览、不加 Ask AI、不加导入，只是信息密度略升，达不到
  「把后端能力在台前展示和可视化」的目标。否决。

## 后果

- 控制台从「12 个运营面板」升级为「总览 + 17 个能力面板 + 全局 Ask AI + 通用导入」，后端能力对用户可见、
  可点、可深链。
- 零新依赖、零前端构建链，门禁与部署路径不变，`scripts/check.py` 仍是唯一入口。
- Ask AI 复用 ADR-0038 的确定性路由，不新增模型不确定性；命中结果可审计、可回放。
- 导入复用既有 registry 验签、RAG 摄取、语义层存储，不新开存储后端。
- 视觉升级是渐进的：先落统一的侧边栏 + 卡片系统，各能力面板复用，不一次性重写全部 HTML。

## 演进路线与建议（待确认）

### MVP（第一阶段）：总览 + 补全 + 导入 + 确定性 Ask AI

1. 视觉基线：侧边栏 + 卡片系统 + 浅色优先主题，升级现有 12 面板的骨架，不新增功能。
2. 总览首页：聚合卡片网格，深链到各面板。
3. 治理能力补全：审计面板 + 配额面板。
4. 构建能力补全：RAG 面板 + 模型网关面板。
5. 语义层面板：术语表、概念、能力绑定、确定性路由回放。
6. 通用导入：术语表 / agent 定义 / RAG 语料三类格式。
7. 全局 Ask AI：确定性语义路由展示 + 深链。

### 第二阶段与触发条件

- **Ask AI 完整编排**（计划结构选择交给模型填空）：当确定性路由已稳定、且出现「同一需求有多种合理计划
  结构」时，接 ADR-0038 第二阶段触发条件再引入。
- **前端框架**：当需要拖拽编排画布、实时拓扑、多人协作等重度交互时，另起 ADR 评估。
- **可视化的实时化**：当总览指标需要秒级刷新或推送时，评估 SSE / WebSocket，MVP 用轮询即可。

## 确认记录（2026-11-22 会话确认）

1. 接受「不引入前端框架，保持无构建的服务端渲染 + CSS 卡片系统」的技术栈决策。
2. 接受「总览首页 + 5 个能力面板 + 通用导入 + 全局 Ask AI」的范围。
3. 接受「Ask AI MVP 只做确定性路由展示 + 深链，不做模型驱动编排」的分界。
4. 接受 MVP 切片顺序（视觉基线先行，导入与 Ask AI 收尾）。
