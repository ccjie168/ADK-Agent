# ADR-0049 异步审批与通知

状态: Accepted   日期: 2026-11-27   签字: 用户（会话确认，2026-11-27）

## 背景

现在所有审批都是同步的：`PlanExecutor` 调 `ApprovalGate.request()` 阻塞等待决策文件或数据库行。
带来的实际问题：

- MCP 工具调用、A2A `message/send` 会被一直挂住，客户端先超时；IM 前端无法先回「已收到」。
- 审批发生前调用方什么都拿不到，也就不可能把 request id 交给用户去控制台处理。
- 审批没有任何主动通知；人不知道有事在等。
- 计划执行进程与审批人之间只能靠轮询同一个存储，没有「决策后继续执行」的通道。

平台的检查点机制已经具备一半条件：`PlanExecutor` 在等待审批时会把
`RunCheckpoint(status="waiting_approval", waiting_step=...)` 写入存储，恢复时用同一
`run_id` 重跑会跳过已完成步骤。本 ADR 决定在这之上做「延迟审批」，而不是新造一套状态机。

理由：业务可用性是当前的第一优先级（用户 2026-11-27 确认把这条排在 ADK 隔离之前），
而「审批不阻塞调用方」是接任何真实前端的前置条件。

## 决定

1. **延迟模式是显式开关**（服务级 `--deferred-approvals`，默认关）。关闭时行为与现在
   逐字节一致；打开时，需要审批的步骤不再阻塞等待。
2. **结果类型**：`PlanExecutor` 在延迟模式下返回 `PlanPending`（`run_id`、`request_id`、
   `step_id`、`expires_at`），不走异常路径；审计写 `orchestration.deferral`（status
   `ok`，target 为步骤 id），不计入 `denied`。`AuditEvent.status` 的词表本期不动；
   若控制台需要 `waiting` 状态，在 0049-2 连同 schema 一起加。
3. **检查点即状态**：延迟时落 `RunCheckpoint(status="waiting_approval", waiting_step,
   approval_request_id)`；恢复用同一个 `run_id` 重跑同一份计划，`plan_digest`
   不一致直接拒绝。
4. **恢复校验**：恢复前核对审批请求的 `tenant`、`run_id`、`step_id` 与输入哈希，任何一项
   不匹配都拒绝恢复并记 `resume_mismatch` 审计。request id 由平台生成，不可猜。
5. **决策交付**：服务进程内有一个 resumer 轮询审批存储（文件或 Postgres），看到终态决策
   就在本进程恢复计划。控制台只负责写决策，不跨进程触发执行，避免引入新的调用面。
6. **通知**：新增 `ApprovalNotifier` 端口，内置两个实现：控制台 SSE 与通用 webhook
   （HMAC 签名，失败重试有限次）。通知失败不影响审批本身；后续 IM 适配器实现同一端口。
7. **到期**：`expires_at` 到期写 `expired`，通知一次，不恢复。
8. **幂等**：一次决策只恢复一次。恢复前以 `run_id` 抢占检查点（条件更新），失败方直接
   退出；恢复失败记 `failed` 并计数告警。
9. **协议面**（分切片交付）：
   - HTTP、MCP 与 A2A 都先立即回执「已提交，等待审批（request_id=…）」，不阻塞调用；
     结果由后台恢复器在决策后继续执行，状态可从控制台「审批」页与运行审计查看。
   - **A2A 任务状态 `input-required` 推迟**（2026-11-28 会话确认，用户选 B）。
     原计划用 `input-required` 任务状态与 `tasks/get` 取回结果，但 ADK 的任务聚合器
     只在收到 `TaskStatusUpdateEvent` 时进入该状态，而普通 `BaseAgent` 的
     `_run_async_impl` 发不出这个事件，需要自定义 A2A 执行器钩子并依赖 ADK 内部行为。
     触发条件：出现真实 A2A 客户端（例如 WorkBuddy 企业版）要求任务语义，且调用方
     无法轮询状态。届时另开 ADR 实现「A2A 执行器钩子」，不在本 ADR 内预写代码。
   - MCP 的 `support_status` 工具推迟到 0049-4；在此之前状态查询走控制台读接口。
10. **权限不变**：审批仍是计划步骤级，不是工具级；工具级审批令牌仍不在本 ADR 范围。

## 切片

1. **0049-1 计划延迟**：`PlanPending`、延迟开关、检查点复用、恢复校验与审计。库层与用例。
2. **0049-2 决策交付与通知**：resumer 轮询、`ApprovalNotifier`（SSE + webhook HMAC）、
   控制台状态与读接口。
3. **0049-3 协议适配与演示**：A2A、MCP 立即回执，售后演示改走延迟模式并在后台恢复；
   A2A `input-required` 按决定 9 推迟。
4. **0049-4 运维**：过期、失败告警、指标、并发与背压说明、手册。

## 后果

- 调用方立即拿到 request id，审批在后台完成，结果通过状态查询或通知取回。
- 计划执行从「一次调用一个连接」变成「可跨请求恢复」，进程重启也能从检查点继续。
- 增量的运维面：resumer 是常驻轮询，需要指标与告警；多副本下同一 `run_id` 的恢复靠
  条件更新保证单赢家，但需要压测确认。
- 审计口径变化：`orchestration.deferral`、`resume_mismatch`、`resume_failed` 是新增动作；
  现有同步路径的审计保持不变。0049-1 只落 `orchestration.deferral` 与
  `approval_request_id`。

## 验收

- 延迟模式下，调用在 2 秒内返回 request id，不占用连接。
- 之后在控制台批准，计划自动恢复并完成建单；调用方通过状态查询或回调拿到结果。
- 同一请求重复决策只恢复一次；重复决策返回 409。
- 到期未处理：写 `expired`、通知一次、不恢复、不留「永不超时」的待批。
- 关闭开关时，现有 2408 条用例全部不变通过。

## 风险与回滚

- 风险：状态机复杂化、恢复并发、跨进程一致性、通知不可靠。
- 回滚：开关默认关；延迟路径与同步路径共用计划执行与审批存储，出问题只关开关。

## 替代方案

- **只做通知、不改阻塞**：解决「人不知道」，不解决客户端超时，不选。
- **另造一套异步任务服务**：与现有检查点重复，不选。
