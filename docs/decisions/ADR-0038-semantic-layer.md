# ADR-0038 语义编排层框架

状态: Accepted   日期: 2026-11-22   签字: Jie CAO（会话确认）

## 背景

平台有两条主线：用户端「无感」的自然语言到 agent 编排，应用端「粘合剂」的 MCP / A2A 互调。两者的
连接点是**语义层**：把用户的自然语言需求，映射到「哪个 agent、用哪个能力、取什么数据」。

现状离这个连接点还差一截：

- 唯一的语义是 `DataClass` 四枚举（`public`/`internal`/`confidential`/`restricted`），它是「数据敏感度」
  本体，不是「业务领域」本体。企业场景词（订单、客户、库存）在平台里没有表达位置。
- 编排是确定性结构（`PlanStrategy` 的 `single`/`sequential`/`routing`/`fan_out`/`supervisor`），
  `core/orchestration.py` 第一句写死「计划是数据，不是 prompt 逻辑」。从需求到计划的自动生成不存在。
- 每个企业的术语不同，同一个概念可能有不同的叫法。没有通用框架时，各企业只能各自定义，映射关系无法
  对齐、无法复用、无法审计。

业内已经收敛出一个共同模式：**本体/语义层是多个 agent 共享的「世界模型」与协调基座，能力映射
（声明每个 agent 能做什么）是核心编排机制**。AWS 的神经符号语义层、FoA（Federation of Agents）的
能力向量、iCARE 的本体驱动意图路由，都在做同一件事：把「语义」和「能力」显式分离，再用映射连接。
术语层的通用标准是 SKOS，能力层的通用标准是 A2A Agent Card 与 MCP 工具描述。本 ADR 不另造标准，
只决定这些标准在本平台里的分层与职责。

## 决定

语义层分四层，从下到上：术语、能力、数据本体、编排。前两层与数据本体是**声明式数据**，可审计可验证；
只有编排层的「需求 → 计划」这一小段允许引入模型，且计划本身仍是数据、有 schema 兜底。

### 1. 术语层：采用 SKOS 的轻量子集

采用 W3C SKOS 的核心结构，但用 JSON 表达，不引入 RDF 三元组存储与 SPARQL：

- **概念（Concept）**：业务领域词，如「订单」「客户」「库存」。
- **标签**：`pref_label`（首选名，每语言一个）、`alt_label`（同义/缩写）、`hidden_label`（拼写变体、
  口语叫法，用于检索不用于展示）。
- **层级**：`broader` / `narrower`（「华东区库存」是「库存」的下位）。
- **跨企业对齐**：`exact_match` / `close_match` 把一家企业的「会员」对齐到另一家的「客户」。

SKOS 的「最小本体承诺」正好是这里需要的：它只做术语与关系，不规定概念的内部语义。这是「每个企业
术语不同、但能对齐到通用概念」的答案。租户各自的术语表可以独立演化，通过 `exact_match` 收敛。

### 2. 能力层：沿用 A2A Agent Card 与 MCP，不自己造

能力声明用业界已收敛的格式，平台在它之上做语义对齐，而不是另立一套：

- A2A Agent Card 的 `skills`（`id`、`name`、`description`、`tags`、`examples`）描述「agent 能做什么」。
- MCP 的 `tools/list`（`name` + `description` + JSON Schema）已经是模型做工具选择时的唯一语义信号。
- 用 dot-namespaced 能力 id（如 `order.lookup`、`inventory.query`）作为术语与工具之间的锚点，兼容
  OpenAI function-calling 与 MCP 工具 schema。

平台现有的 `manifest.tool_grants`、A2A peer、MCP server 已经携带了能力声明，本层要补的是**把能力 id
和术语层的概念显式关联**，而不是新建一套能力模型。

### 3. 数据本体层：在「敏感度」之上加一维「领域」

现有 `DataClass` 只有「敏感度」一维。本 ADR 把它扩成正交的两维：

- **敏感度**（`public`/`internal`/`confidential`/`restricted`）保持平台固定枚举。它关系安全与审计，
  必须可验证，不能由租户自由定义。
- **领域**（订单/客户/库存……）用租户可扩展的概念，落到术语层的概念，默认词汇用 Schema.org 的业务
  实体作为骨架。一个数据同时有所属领域与敏感度，两者正交。

这样「确定性 vs 可扩展」的张力被拆开：可审计的部分固定，灵活的部分开放，而不是二选一。

### 4. 编排层：语义路由 + 确定性计划

「需求 → 计划」新增一步语义路由，其余不变：

- 需求文本先经术语层归一到概念，再经能力层映射到候选 agent/工具，这一步是**确定性**的（术语、能力、
  映射关系都是显式定义）。
- 只有「计划结构怎么选」（`routing` 还是 `fan_out`、几个 agent 协作）允许模型填空，但输出必须落到
  现有 `PlanStrategy` 的 schema，由 `PlanExecutor` 校验后执行。计划仍是数据，不是 prompt 逻辑。
- 语义路由的结果可审计：需求 → 概念 → 能力 → 计划，每一步都是可追溯的显式映射。

## 备选与否决

- **完整 OWL/RDF 知识图谱 + 推理。** 表达力最强，但企业落地成本高，需要三元组存储与推理器，MVP 用
  不上。语义层的「映射」用 SKOS 子集与显式关联就能覆盖。否决（可留作远期演进）。
- **纯模型驱动端到端拆解。** 灵活，但不可审计、不可验证、不可复现，与平台一贯的确定性基调冲突。
  否决，只保留编排层最后一小段允许模型参与。
- **全平台固定枚举（现状）。** 僵化，企业无法表达自己的领域语义，语义层就名存实亡。否决。
- **完全租户自由文本。** 无结构，无法保证映射准确，也无法审计。否决。

## 后果

- 术语层、能力层、数据领域层都是纯声明式数据，可审计、可验证、可测试，不引入新的不确定性。
- 编排层新增的语义路由是唯一引入模型不确定性的点，用 schema 兜底，失败可追溯。
- 现有的 `DataClass`、`manifest`、`tool_grants`、A2A、MCP 全部保留，语义层是在它们之上加对齐，不是
  推倒重来。`DataClass` 的既有语义不变，只是旁边多了一维领域。
- 术语表与领域本体的存储、版本化、跨租户隔离、以及「映射准确」的验证方法，需要后续切片明确，本 ADR
  只定框架与职责边界。

## 演进路线与建议（待确认）

MVP 与第二阶段的分界，以及四个待确认项的建议如下。

### MVP（第一阶段）：声明式三层 + 确定性映射

1. 术语层、能力层、数据领域维三层只做声明式实现，不引入模型行为。
2. 编排层只做确定性的「术语 → 概念 → 能力 → agent」映射；计划结构选择仍走现有 `PlanStrategy` 的
   显式定义，不做模型填空。
3. 存储沿用 registry 的 Postgres / 文件双后端，天然获得租户隔离、多副本与审计链。不单开一套。
4. 领域默认词汇挂一小撮 Schema.org 业务实体（Order、Customer/Person、Product 等）作起步骨架，
   领域概念本身租户可扩展，不强制绑定 Schema.org。
5. 验收用结构性契约测试：术语层级无环、标签唯一、能力 id 不悬空（每个能力 id 都能回溯到真实的
   `tool_grants` 或 A2A skill）、领域与敏感度两维正交。不需要标注数据。

### 第二阶段与触发条件

- **语义路由模型化**（计划结构选择交给模型填空）：当确定性映射已稳定、且出现「同一需求有多种合理
  计划结构、确定性规则写不完」的场景时再引入。计划仍是数据、有 schema 兜底。
- **独立图存储 / 推理器**：当术语规模大到关系表 + JSON 不够，需要跨企业 `exact_match` 的图遍历或
  本体推理器时再评估。MVP 的术语规模用关系表足够。
- **标注数据验收**：模型参与语义路由后，用一组带标注的「需求 → 期望计划」对评测准确率；在此之前
  契约测试已覆盖确定性的部分，不需要标注数据。

## 确认记录（2026-11-22 会话确认）

1. 接受「语义层分四层：术语、能力、数据本体、编排」，前三层声明式、编排层仅语义路由一小段允许模型。
2. 接受「敏感度固定、领域可扩展」的两维正交，`DataClass` 语义不变。
3. 接受 MVP 演进路线：第一阶段只做声明式三层 + 确定性映射，不引入模型行为。
4. 接受四个建议：存储沿用 registry 双后端；语义路由模型化放第二阶段；领域挂 Schema.org 骨架且租户可扩展；
   MVP 用结构性契约测试验收，第二阶段才用标注数据。
