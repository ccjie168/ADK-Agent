# ADR-0024 agent 级沙箱：进程隔离、资源上限与出口中介

状态: Accepted   日期: 2026-11-17   签字: Jie CAO（会话确认）

## 背景

ADR-0022 第 4 条把租户自带代码挡在门外，条件是先有单独的 ADR 定义隔离方式、资源上限、出站策略与运行身份。这份 ADR 回答该条件。

现状有三个事实。

- `registry/loader.py` 在平台进程里 `exec` 已签名工件。签名回答的是“谁批准运行”，不回答“代码安全”。一个被批准、被评测通过的工件仍然可以读 `os.environ`、删文件、连外网。
- `sandbox/` 已有进程隔离：每次工具调用起子进程、POSIX `RLIMIT`、清空环境、socket 守卫。它只覆盖工具源，且按单次函数调用设计。
- 声明式组合器（SLICE-123）从模板生成代码，走同一条 loader。这部分代码由平台模板产生，可信度与租户手写代码不同。

不决定的代价是明确的。要么保持现状，租户代码永远不能进平台。要么把任意代码当配置直接放开，用一个签名当安全证明。

## 决定

1. **工件声明执行层级。** `AgentManifest` 新增 `execution_tier`，取值 `in_process` 或 `sandboxed`，必填，未知值拒绝。代码优先的 `publish` 默认 `sandboxed`；只有平台模板生成器（组合器）可以声明 `in_process`。契约先改，再改实现。
2. **沙箱边界是一个独立的 worker 进程。** 每次 agent 运行由可信服务 `spawn` 一个子进程，工件的 `exec` 与运行都在子进程内完成。父进程保留注册表、信任根、生命周期、配额、审计、会话存储与工具守卫。worker 按次数回收，异常后直接丢弃，不复用脏进程。
3. **worker 无网络。** 模型调用与工具调用都通过一条类型化的管道协议回到父进程。父进程按租户模型白名单、工具授权、审批状态、配额与审计规则执行，再把结果送回。worker 不持有凭据，也不解析 `secret://`；密钥只在父进程发起工具调用时解析。
4. **资源上限与运行身份。** 每次运行有墙钟超时、CPU 秒数、地址空间、子进程数、打开文件数与单文件大小上限，写盘只允许一次性的临时目录，运行结束即删除。环境变量清空，只保留显式白名单。只读的文件系统视图与内核级隔离不在 v1 范围内，见第 9 条。
5. **平台前提。** `sandboxed` 层级要求有 `RLIMIT` 的 POSIX 系统与专用非特权服务账号；服务以 root 运行时 worker 降到配置的 uid。生产启动时做能力探测，探测失败则拒绝加载 `sandboxed` 工件。Windows 只允许本地开发，且必须显式 `--allow-unsandboxed`，该降级要写日志与审计。
6. **不直接复用工具沙箱。** 两者作用对象、生命周期与出口都不一样：工具是单次同步调用，agent 是长运行、多轮、要流式事件与模型出口。共享底层原语（环境清空、限制设置、网络守卫），但 agent 沙箱有自己的 worker 入口、协议与中介层。
7. **沙箱在信任链之下，不替代它。** 签名、信任根、生命周期、审批、评测门禁照旧生效。沙箱只降低“已批准代码”的爆炸半径。
8. **失败语义。** 越权、超时、崩溃分别映射为 `sandbox_violation`、`sandbox_timeout`、`sandbox_crashed`，写审计事件，按运行失败处理，不自动重试。这与 SLICE-127 的“agent 运行失败不重试”一致。
9. **残余风险与开放条件。** v1 不是内核级隔离。内核漏洞、同 uid 的文件系统读取、同 uid worker 之间的 ptrace 都不在防护范围内；v1 的目标是挡住平台密钥、网络与持久化副作用，不挡内核攻破。把租户代码开放给不受信网络调用方之前，必须有容器或虚拟机层级，那需要另一份 ADR。在此之前，`sandboxed` 工件是运维控制的内部能力。

## 备选与否决

- **直接复用工具沙箱**：入口、协议、出口都不同，强行复用会把两种威胁模型搅在一起；否决。
- **一开始就上容器或微虚机**：新增运行时依赖与运维面，Python 3.14 镜像与 GPU/模型网关的接入都要重做；暂缓，作为第 9 条的下一层。
- **Wasm 或 Pyodide 运行 agent**：与 ADK 及模型客户端不兼容，依赖重；否决。
- **只靠代码评审与签名放行**：签名只证明批准过，不限制运行期行为；否决。
- **所有工件立刻迁入沙箱**：平台生成的工件也要付进程与协议成本，且会把迁移和沙箱设计耦合；先用 `execution_tier` 分开，再逐步迁移。
- **每个租户一个系统用户**：隔离更强，但部署与文件权限复杂，v1 用单一专用账号加 rlimit；暂缓。

## 后果

- 每次运行多一次进程启动与管道往返，流式输出需要协议层支持，`serve`、`trigger`、A2A 与评测路径都要改走同一条沙箱感知的执行路径。
- 会话服务留在父进程，worker 内需要一个代理实现，ADK 升级时要复核该接口。
- Windows 开发环境失去完整对等，测试里的恶意工件用例只能在 POSIX 或 CI 的 Linux runner 上验证隔离效果。
- 组合器输出继续保持 `in_process`，因此组合模板本身成为信任边界的一部分，模板变更要按安全变更评审。
- 多了运行手册内容：能力探测、worker 回收、越权事件告警与本地降级开关。

## 切片

进入时分配编号，预计顺序如下。

- 契约与层级：manifest 增加 `execution_tier`，发布路径默认 `sandboxed`，能力不可用时拒绝。
- worker 与协议：独立进程加载与单轮运行，超时、越权与崩溃映射，恶意工件用例（联网、超配额、读环境、逃逸临时目录、fork 炸弹）。
- 出口中介：模型与工具调用经父进程执行，配额、审批与审计留在可信侧。
- 接入与收口：`serve`、触发服务、A2A 与评测走同一路径，控制台状态、运行手册与证据文件。
