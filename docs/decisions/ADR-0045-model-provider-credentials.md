# ADR-0045 模型提供方与密钥配置

状态: Accepted   日期: 2026-11-25   签字: Jie CAO（会话确认，见文末）

## 背景

现在「模型」页只配置全局默认模型标识（`provider:name`），密钥只能从进程环境变量读取
（`DEEPSEEK_API_KEY`、`GOOGLE_API_KEY` 等）。用户希望能在配置页管理模型接入与密钥。

平台已有的密钥基础设施：

- `secretstore` 提供 KEK 信封加密（本地 keyring）与 Vault/OpenBao Transit 两种后端；
- 连接器与凭据只保存 `secret://...` 引用，值由服务端环境或 secretstore 提供；
- 凭据写入已有“只写不读”的先例（控制台拒绝请求体密文、列表只回掩码元数据）。

本 ADR 决定模型提供方的配置形态：**只存引用**，还是**允许只写加密录入**。

## 决定

### 1. 新增「模型提供方」记录

无论选哪个方案，都新增一条记录形状：

| 字段 | 说明 |
|---|---|
| `provider_id` | 安全名，如 `deepseek-prod` |
| `kind` | `litellm` / `gemini` / `claude` / `vertex` |
| `base_url` | 可选，Anthropic 兼容端点等 |
| `model` | `provider:name` 或该提供方下的默认模型 |
| `secret_ref` | `secret://...` 引用（方案 A）或内部加密记录 id（方案 B） |
| `enabled` | 停用后不参与解析 |
| `updated_at` / `updated_by` | 审计用 |

解析顺序（替代现在的环境变量直读）：

1. 记录里显式指定的提供方与模型；
2. 环境变量（`ADK_AGENT_MODEL` 与各 provider key）；
3. 内置默认（`litellm:deepseek/deepseek-v4-pro`）。

接口挂 `model.read` / `model.write`（仅 admin 写）；每次变更写 `model.configure` 审计，
只记录提供方 id、类型与 `secret_ref` 的键名，**不记录密钥值、不记录密文**。

### 2. 方案 A：纯引用（推荐为默认）

页面只填 `secret_ref`，密钥值由部署环境或 secretstore 提供：

- 本地 deployment：`ADK_SECRET_KEKS` 加密的凭据文件，或进程环境变量；
- Vault/OpenBao 部署：Transit 解密，平台只持有引用。

优点：模型配置里没有任何密钥材料；与连接器/凭据的既有模型一致；轮换与吊销沿用
secretstore 的流程；被拖库时模型配置没有额外价值。

缺点：录入是两步（先放 secret，再填引用）；手机上操作略繁琐。

### 3. 方案 B：只写加密录入（可选、显式开启）

admin 在页面提交一次 `api_key`，平台用 KEK 或 Vault Transit 加密后保存：

- `POST /api/model-providers` 接受 `api_key`，**只写**；
- `GET` 系列只返回掩码（`sk-…abcd`）、更新时间与是否可用，任何接口不回明文或密文；
- 运行时按需解密，解密失败 fail-closed 并审计 `model.key_failed`（不含值）；
- 需要部署已配置 keyring（`ADK_SECRET_KEKS` 或 Vault Transit），否则端点 503。

优点：一页完成接入，手机上可操作；密钥不出平台，轮换在同一处。

缺点：平台因此成为模型密钥的托管方；备份、数据目录、审计与日志都成了需要保护的对象
（见下节）；密钥泄露的影响面比方案 A 大。

### 4. 推荐

- **默认方案 A**：生产与多租户部署只允许引用。
- **方案 B 作为显式选项**：由启动参数（例如 `--model-key-entry`）开启，默认关闭；
  开启后在页面上标注“平台托管密钥”，并在审计里单独标记。
- 两者共用同一套记录、解析顺序与 RBAC；方案 B 只是 `secret_ref` 的另一种来源。

## 关于「加密录入后上传 GitHub 会不会泄露」

会有真实风险，且风险不在“别人直接读到明文”，而在以下几处：

1. **密文进 Git 历史**：如果模型配置的数据目录落在仓库里（例如 `--model-config-dir ./data`），
   加密记录会被提交。Git 历史无法真正删除，轮换前的密文永久可查；一旦 KEK 同时泄露
   （环境变量、部署清单、CI Secret 配置失误），历史里的密文就可解密。
2. **测试与演示数据**：用手工构造的“示例密钥”开发时，容易把真实 key 贴进测试夹具或
   `.env` 示例文件。
3. **日志与错误信息**：解密失败、HTTP 客户端报错可能携带请求头或 URL；审计若记录请求体
   就会落盘。
4. **备份与快照**：`backup` 归档、容器镜像层、CI artifact 都可能带走数据目录。
5. **导出接口**：任何“导出配置”功能如果不剔除密文，等于把托管密钥复制出去。

对应的强制措施（方案 B 的前提条件，写进契约与测试）：

- 模型配置存储路径必须在仓库之外；启动时检测路径落在仓库根目录内则拒绝启动（新增检查）。
- `.gitignore` 覆盖常见数据目录；门禁的 secrets 扫描继续保留，但它只拦明文特征，不能替代路径检查。
- 任何读接口不返回明文与密文；导出与备份只含 `secret_ref` 与掩码。
- 审计、日志、异常信息统一脱敏；测试夹具只用明显假的 `sk-test-…` 值。
- 密钥轮换是一等操作；泄露处置以“轮换 + 吊销”收尾，不依赖删除 Git 历史。

结论：方案 B 能做得足够安全，但它把平台升级为密钥托管方，必须同时落实上面的存储路径检查
与只写接口；做不到就不要开方案 B，用方案 A。

## 切片

- SLICE-296：记录形状、`GET/PUT /api/model-providers`（方案 A），契约与审计，解析顺序改造。
- SLICE-297：方案 B（`--model-key-entry`、只写录入、掩码读、解密失败审计、repo 内路径拒绝启动）。
- SLICE-298：控制台「模型」页提供方表单与状态展示；手册补一章。

## 备选与否决

- **继续只支持环境变量**：手机端无法自助接入新模型，用户明确要页面配置。否决。
- **密钥存明文配置**：违反仓库禁区与常识。否决。
- **页面读取任意 secret_ref 指向的明文**：等于变成通用秘密读取接口。否决；只允许模型运行时解密。
- **默认开启方案 B**：把所有部署都变成密钥托管方。否决。

## 后果

- 模型接入从“改环境变量重启”变成“页面配置 + 引用（可选加密录入）”。
- 新增一份需要保护的存储：模型提供方记录；泄漏影响面小于凭据，但同样纳入备份与审计范围。
- 手机端可以自助切换模型；切换写 `model.configure` 审计。

## 确认记录

- 2026-11-25：用户要求起草本 ADR，并询问加密录入在 GitHub 上的泄露风险。
- 2026-11-25：用户确认 A + B 都做：方案 A 为默认（SLICE-296），方案 B 用启动参数显式开启
  （SLICE-297/298），并接受方案 B 的五条前提（存储必须在仓库外且启动时拒绝仓库内路径、
  读接口不返回明文或密文、审计与日志脱敏、轮换吊销兜底、仅 admin 且 KEK 未配置时 503）。
